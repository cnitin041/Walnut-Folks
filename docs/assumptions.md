# Assumptions and Design Decisions

This document records the choices that are not fully prescribed by the assessment and the behavior callers should expect.

## Monetary precision

- Monetary values are stored as PostgreSQL `NUMERIC(18, 2)` and handled as Python `Decimal`.
- API requests and responses represent money as JSON strings, for example `"125.50"` or `"0.00"`.
- JSON floating-point values are rejected for amounts and balances. Integers such as `100` and decimal strings such as `"100.00"` are accepted.
- Amounts must be greater than zero and may have at most two decimal places. Balances must be non-negative.
- The largest supported balance is `9999999999999999.99`, matching `NUMERIC(18,2)`. Credits and transfers that would exceed it return `400 BALANCE_LIMIT_EXCEEDED` instead of causing a database overflow.
- Binary floating point is never used for money.

## Timestamp generation and timezone

- `created_at` values are generated by PostgreSQL with `now()` on `TIMESTAMP WITH TIME ZONE`.
- Clients cannot set transaction, transfer, or account timestamps.
- Responses serialize timestamps as ISO-8601 strings with an offset, for example `2026-10-27T11:54:49.252351+05:30`.
- Ordering uses `created_at DESC, id DESC` so equal timestamps still have a deterministic order.

## UUID generation

- Account, transaction, and transfer IDs are UUID version 4 values generated in Python with `uuid.uuid4()` before insertion.
- IDs are not supplied by clients.
- Unknown UUIDs return `404` where an account is expected. Malformed UUIDs return `422`.

## Account balance model

- `accounts.balance` is a cached aggregate for fast reads.
- The `transactions` table is the immutable source of truth.
- For every account:

  ```text
  balance = sum(credits) - sum(debits)
  ```

- A successful credit or debit inserts exactly one ledger entry and updates the cached balance in the same database transaction.
- A failed operation inserts no ledger entry and changes no balance.

## Duplicate reference handling

- Transaction references are unique per account through `UNIQUE(account_id, reference_id)`.
- The same transaction reference is allowed on different accounts.
- A duplicate transaction reference for the same account returns HTTP `409` with code `DUPLICATE_TRANSACTION`.
- Concurrent duplicate submissions are serialized by the account row lock. The database unique constraint remains the final protection; a constraint violation is translated to the same `409` response.
- Transfer references are globally unique through `UNIQUE(transfers.reference_id)`. A duplicate returns HTTP `409` with code `DUPLICATE_TRANSFER`.
- The pre-insert duplicate checks improve error messages and avoid unnecessary work. They are not the only protection.

## Idempotency behavior

- Duplicate prevention is implemented, not full idempotent replay.
- Repeating a transaction or transfer with an already-used reference returns `409` and does not move money again.
- The API does not return the original successful response for a repeated reference. Clients that need replay semantics should treat `409` as an indication that the reference was already processed and query the ledger before retrying with a new reference.
- Transfer ledger entries use derived references `transfer:<transfer_id>:debit` and `transfer:<transfer_id>:credit`. This guarantees unique ledger references and keeps them visibly linked to the transfer.

## Transaction immutability

- There are no update or delete endpoints for accounts, transactions, or transfers.
- The API exposes no path that edits or removes a historical ledger entry.
- Foreign keys use `ON DELETE RESTRICT`, so ledger rows cannot be cascaded away by deleting an account.
- A PostgreSQL trigger that rejects `UPDATE` and `DELETE` on `transactions` is not included. It is a recommended production hardening step for operators with direct database access.

## Pagination defaults and limits

- `page` defaults to `1` and must be at least `1`.
- `limit` defaults to `10` and must be between `1` and `100`.
- Pagination is applied in SQL with `LIMIT` and `OFFSET`.
- `total_records` is the count of the filtered result set.
- `total_pages` is `ceil(total_records / limit)`, or `0` when there are no matching records.
- A page past the end returns an empty `data` array while preserving the real total counts. This is preferred over returning an error because it keeps navigation predictable.
- History supports only the `type` filter. Date-range filtering is not part of this implementation.

## HTTP status-code conventions

| Status | Use |
| --- | --- |
| 200 | Successful retrieval |
| 201 | Successful account, transaction, or transfer creation |
| 400 | Business-rule violation: insufficient balance, balance limit exceeded, or same-account transfer |
| 404 | Missing account or unmatched route |
| 405 | Unsupported method on an existing route |
| 409 | Duplicate reference or conflicting database state |
| 422 | Invalid request body, UUID, query parameter, or pagination |
| 500 | Unexpected server failure |
| 503 | Health check reports the database unavailable |

The API uses a consistent error envelope:

```json
{
  "success": false,
  "error": {
    "code": "INSUFFICIENT_BALANCE",
    "message": "Insufficient balance for this debit transaction.",
    "details": {}
  }
}
```

`details` is optional. Validation errors include a list of field-level errors. Internal SQL, credentials, and stack traces are never returned to clients.

## Transfer reference uniqueness

- Every successful transfer creates one `transfers` row with a globally unique client-supplied `reference_id`.
- Exactly two ledger entries reference that transfer: one debit on the source account and one credit on the destination account.
- `UNIQUE(transfer_id, type)` guarantees at most one debit and one credit per transfer.
- The transfer row, both ledger entries, and both cached balance changes commit in one database transaction.
- If any part fails, the entire transaction rolls back. A partial transfer cannot be committed.

## Balance consistency strategy

- Cached balances are updated only inside the same transaction that writes the ledger entry.
- The automated test suite recomputes every account balance from all ledger entries and compares it with the stored balance. It also verifies that transfer ledger totals are balanced.
- In production, a scheduled reconciliation job should:
  1. Recompute each account balance from the ledger with a consistent snapshot.
  2. Compare the result with `accounts.balance`.
  3. Record and alert on any mismatch with account ID, expected balance, stored balance, and the time window.
  4. Investigate before changing anything. Do not silently edit or delete historical ledger entries.
  5. If a correction is required, append explicitly referenced compensating ledger entries and update the cached balance in the same transaction.
  6. Rebuild cached balances from the ledger only as a controlled maintenance operation after the cause is understood and the ledger is verified.
- Balance corrections must be auditable and append-only. Historical entries are never rewritten.

## Concurrency and locking strategy

- Each request uses one SQLAlchemy session and one database transaction per business operation.
- Credit and debit operations lock the account row with `SELECT ... FOR UPDATE` before checking the reference, validating funds, inserting the ledger entry, and updating the balance.
- This serializes concurrent writes to the same account, so a debit cannot use a stale balance and duplicate references cannot both commit.
- Transfers lock both account rows in ascending UUID order before doing any work. Consistent lock order prevents the classic deadlock where two opposite transfers each hold one account and wait for the other.
- PostgreSQL's default `READ COMMITTED` isolation is used. Row locks plus the constrained update are sufficient for these operations; no application-level locks are used.
- Unique constraints are the final protection against concurrent duplicates. `IntegrityError` is caught only after the session is rolled back, and duplicate constraint violations are translated to `409`.
- Services use `session.begin()` to avoid nested or accidental transactions. Early business-rule exits roll back the transaction, releasing account locks.
- No automatic retry loop is implemented. Deadlocks are avoided by deterministic lock ordering; serialization failures are not expected under the default isolation level for these row-lock operations.

## Validation choices

- Unexpected fields are rejected by request schemas (`extra="forbid"`), including client-supplied balances, timestamps, and IDs.
- Account names are stripped of surrounding whitespace and must contain 1-255 characters.
- Descriptions are optional, stripped, and limited to 1000 characters. They default to an empty string.
- Reference IDs are stripped, required, and limited to 255 characters.
- Transfer source and destination must be different. The same-account check runs before account existence checks, so an identical nonexistent UUID returns `400 SAME_ACCOUNT_TRANSFER` rather than `404`.

## Health endpoint

- `GET /health` executes `SELECT 1` against the configured database.
- A healthy process with an unavailable database returns HTTP `503` and `{"status": "degraded", "database": "unavailable"}` rather than reporting the application process as healthy.
- A successful check returns `{"status": "ok", "database": "ok"}`.

## Tests and environment

- Tests run against PostgreSQL, not SQLite, because row-level locking and constraint behavior must match production.
- The test database is isolated through `TEST_DATABASE_URL`. The suite applies Alembic migrations and truncates only `accounts`, `transfers`, and `transactions` between tests.
- Concurrency is exercised with parallel HTTP requests through FastAPI's HTTPX-based test client. This is not a production load or soak test.
- The local PostgreSQL cluster and Docker Compose use trust authentication restricted to localhost for developer convenience. Production deployments should use managed credentials and TLS.

## Deviations and out-of-scope items

- No authentication or authorization is implemented, as the assessment does not require it.
- No account listing, account update, account deletion, transaction update, transaction deletion, transfer retrieval, or transfer listing endpoints are provided.
- The ledger is single-currency; currency codes, FX conversion, fees, and settlement states are not modeled.
- There is no rate limiting, request ID propagation, metrics endpoint, or structured JSON logging. Logging is standard text logging with timestamps, levels, logger names, and messages.
- A database trigger enforcing ledger immutability is not included; API-level immutability and restrictive foreign keys are.
- Duplicate submissions return `409` rather than the original resource. Full idempotency-key replay behavior is not implemented.
